# Legacy architecture and business rules

This document records how the legacy BankSystem microservices behave **today**, before the
Java 21 / Spring Boot 3 migration. Every business rule has a stable ID (`LEG-xx`) so later
phases can write a named acceptance test per rule (e.g. `LEG_03_nonOverdraftBillRejectsNegativeBalance`).
The "Suspected quirks" section lists behaviour that may be a defect; each is labelled
**Confirmed** or **Not confirmed** against the code. They are recorded for a human decision,
not fixed here.

All line references are against `master` at the time of writing. Path prefixes:

| Prefix | Path |
|---|---|
| `AS/` | `AccountService/src/main/java/ru/kondrashov/accountservice/` |
| `PS/` | `PersonService/src/main/java/ru/kondrashov/personservice/` |
| `CS/` | `CommonService/src/main/java/ru/kondrashov/commonservice/` |
| `AS-res/`, `PS-res/`, `CS-res/` | `<Service>/src/main/resources/` |

## 1. System overview

| Service | Port | Responsibility | Storage |
|---|---|---|---|
| CommonService | 8080 | Thymeleaf web UI and orchestration (`/common/v1/...`, `CS/controllers/CommonController.java:20`) | none |
| AccountService | 8081 (`AS-res/application.yml:9`) | Accounts, bills, payments, adjustments, transfers (`/v1/people/{personId}/accounts`, `AS/controllers/AccountsController.java:24`; `.../bills`, `AS/controllers/BillsController.java:27`) | PostgreSQL `account-service-db` |
| PersonService | 8082 (`PS-res/application.yml:9`) | People (`/v1/people`, `PS/controllers/PeopleController.java:25`) | PostgreSQL `person-service-db` |

Stack (each service is an independent Maven project, no parent POM): Java 8
(`AccountService/pom.xml:27`), Spring Boot 2.4.4 (`AccountService/pom.xml:8`), Spring Data JPA /
Hibernate, PostgreSQL, Thymeleaf (CommonService only), Lombok, Log4j2, Springfox Swagger 2.7.0
(`AccountService/pom.xml:105`), Moneta 1.4.2 for currency conversion (`AccountService/pom.xml:114-115`).
Schema is generated by Hibernate at start-up (no migration tool, see Q3).

### 1.1 Call graph

```
Browser ──HTML──> CommonService :8080
                    │  RestTemplate (CS/config/ApplicationConfig.java:13)
                    ├──> PersonService  :8082  people.URL, person.URL
                    └──> AccountService :8081  accounts.URL, account.URL, bills.URL, bill.URL, transactions.URL
```

CommonService has no database. All data access goes through `CommonServiceImpl`, which formats the
URL templates from `CS-res/application.yml:1-7` with `String.format` and calls them with `RestTemplate`:

| Template (`CS-res/application.yml`) | Target | Used by (`CS/services/CommonServiceImpl.java`) |
|---|---|---|
| `people.URL` (:1) | PersonService `GET/POST /v1/people` | `getPeople` :48-51, `createPerson` :105-108 |
| `person.URL` (:2) | PersonService `GET/PUT/DELETE /v1/people/{id}` | `getPersonById` :42-43, `updatePerson` :142-147, `deletePerson` :182 |
| `accounts.URL` (:3) | AccountService `GET/POST .../accounts` | `getAccountsByPerson` :62-65, `createAccount` :117-120 |
| `account.URL` (:4) | AccountService `PUT/DELETE .../accounts/{id}` | `updateAccount` :152-157, `deleteAccount` :187-192 |
| `bills.URL` (:5) | AccountService `GET/POST .../bills` | `getBillsByAccountId` :76-79, `createBill` :129-132 |
| `bill.URL` (:6) | AccountService `PUT/DELETE .../bills/{id}` | `updateBill` :163-168, `deleteBill` :197-202 |
| `transactions.URL` (:7) | AccountService `GET .../bills/{id}/transactions` | `getFinancialTransactionsByBillId` :90-93 |

There is no service discovery, retry, timeout, circuit breaker or auth on these calls; host/ports
are hard-coded to `localhost`. CommonService never calls the payment/adjustment/transfer endpoints;
those are only reachable on AccountService's REST API directly.

Single-item pages fetch the whole parent collection and filter in memory, e.g. account page
(`CS/controllers/CommonController.java:42-51`) and bill page (`:58-67`); an id that is not in the
list raises a `RuntimeException`.

## 2. Data model

PersonService and AccountService have separate databases. The only link between them is the
`personId` UUID column on `Account`; there is no foreign key or cross-service consistency check.

| Entity | Table | Fields | Source |
|---|---|---|---|
| `Person` | `public.people` | `id` UUID (generated), `firstName`, `lastName`, `birthdate` (LocalDate), `phoneNumber`, `email` | `PS/entities/Person.java:18-45` |
| `Account` | `public.accounts` | `id` UUID, `name`, `creationDate` (LocalDate, `@CreatedDate`), `personId` UUID | `AS/entities/Account.java:20-40` |
| `Bill` | `public.bills` | `id` UUID, `currency` (java.util.Currency), `amount` BigDecimal default `0`, `isOverdraft` Boolean, `account` (FK `account_id`, `ON DELETE CASCADE`) | `AS/entities/Bill.java:19-38` |
| `FinancialTransaction` (mapped superclass) | — | `id` UUID, `currency`, `amount` BigDecimal, `time` LocalDateTime default `now()`, `message` | `AS/entities/FinancialTransaction.java:19-37` |
| `Payment` | `public.payments` | superclass + `bill` (FK, `ON DELETE CASCADE`) | `AS/entities/Payment.java:22-29` |
| `Adjustment` | `public.adjustments` | superclass + `bill` (FK, `ON DELETE CASCADE`) | `AS/entities/Adjustment.java:15-22` |
| `Transfer` | `public.transfers` | superclass + `sourceBill`, `beneficiaryBill` (both FK, `ON DELETE CASCADE`) | `AS/entities/Transfer.java:17-30` |

All `@ManyToOne` associations are `FetchType.EAGER` with `CascadeType.MERGE`
(e.g. `AS/entities/Bill.java:34`, `AS/entities/Transfer.java:20,26`). A "bill" is the balance-holding
sub-account in a single currency; an account can have many bills.

## 3. Business rules

| ID | Rule (as implemented) | Source |
|---|---|---|
| LEG-01 | **Payment debits a bill.** The payment amount is converted from the payment currency into the bill currency (LEG-07), subtracted from the bill balance, the bill is saved, then the `Payment` row is saved. Endpoint `PUT .../bills/{billId}/payments` returns `202 Accepted`. | `AS/services/BillServiceImpl.java:75-82`, `:119-127`; `AS/controllers/BillsController.java:95-104` |
| LEG-02 | **Overdraft bills may go negative.** If `bill.isOverdraft` is `true`, a debit is applied with no lower bound. | `AS/services/BillServiceImpl.java:123` |
| LEG-03 | **Non-overdraft bills cannot go negative.** If `isOverdraft` is `false` and the balance *after* subtraction is `< 0`, `NotEnoughMoneyException` is thrown before `billsRepository.save`. A balance of exactly `0` is allowed. | `AS/services/BillServiceImpl.java:121-127` |
| LEG-04 | **Insufficient funds → HTTP 400.** `NotEnoughMoneyException` is mapped to `400 Bad Request` with body `{message, 400, "NotEnoughMoneyException"}`. Payment rollback relies on `@Transactional(rollbackFor = Exception.class)` on `commitPayment`. | `AS/exceptions/handler/AccountServiceExceptionHandler.java:36-43`; `AS/services/BillServiceImpl.java:75` |
| LEG-05 | **Adjustment credits a bill.** Amount converted to the bill currency (LEG-07), added to the balance, bill saved, then the `Adjustment` row saved. No overdraft/limit check. `PUT .../bills/{id}/adjustments` → `202`. | `AS/services/BillServiceImpl.java:65-71`, `:130-132`; `AS/controllers/BillsController.java:107-116` |
| LEG-06 | **Transfer moves money between two bills.** Loads source and beneficiary; debits the source by the amount converted to the source currency (applies LEG-02/LEG-03), credits the beneficiary by the amount converted to the beneficiary currency, then saves the `Transfer`. Each currency is converted independently from the transfer currency. No check that source ≠ beneficiary or that both bills belong to the path's person/account. `PUT .../bills/{sourceId}/transfer/{beneficiaryBillId}` → `202`. Atomicity: see Q1/Q2. | `AS/services/BillServiceImpl.java:87-95`; `AS/controllers/BillsController.java:119-129` |
| LEG-07 | **Currency conversion** goes through `JavaMonetaApiCurrencyExchange.exchange(from, to, amount)`: builds a Moneta `MonetaryAmount` in the source currency, converts with `MonetaryConversions.getConversion(targetCurrencyUnit)` (default provider chain), and returns a `BigDecimal`. Conversion is applied even when source and target currency are equal. | `AS/services/JavaMonetaApiCurrencyExchange.java:26-34` |
| LEG-08 | **Rounding:** the converted amount is rounded with `new MathContext(2, RoundingMode.HALF_EVEN)` (banker's rounding, **2 significant digits**). This result is what is added to / subtracted from balances. See Q6. | `AS/services/JavaMonetaApiCurrencyExchange.java:34` |
| LEG-09 | **Bill update re-denominates the balance.** `PUT .../bills/{id}` sets the stored balance to `exchange(oldCurrency, newCurrency, newBill.amount)` — i.e. the *submitted* amount is treated as being in the old currency and converted to the new one — then overwrites currency, overdraft flag and account. | `AS/services/BillServiceImpl.java:55-61` |
| LEG-10 | **Transaction history** for a bill (`GET .../bills/{id}/transactions`) is the union of adjustments (positive), payments (negated), transfers where the bill is beneficiary (positive) and transfers where it is source (negated). Amounts are shown in the transaction's own currency, not the bill's. No sort order is applied. | `AS/controllers/BillsController.java:132-172` |
| LEG-11 | **Transaction amount validation:** request DTOs use `@Min(value = 0)`, so `0` is accepted and only negative amounts are rejected (message says "more than zero"). `currency` and `message` are required. | `AS/controllers/dto/PaymentRequestDTO.java:23-33`; `AS/controllers/dto/TransferRequestDTO.java:23-33`; `AS/entities/FinancialTransaction.java:28-37` |
| LEG-12 | **New bills start at zero** (`amount = BigDecimal.ZERO`) unless an amount is supplied; `currency`, `isOverdraft` and `account` are required. | `AS/entities/Bill.java:27-38`; `AS/controllers/dto/BillRequestDTO.java:19-27` |
| LEG-13 | **Cascading person deletion is orchestrated by CommonService.** `deletePerson` first lists the person's accounts from AccountService and issues one `DELETE` per account, then `DELETE`s the person in PersonService. Deleting an account cascades to its bills and their payments/adjustments/transfers via DB-level `ON DELETE CASCADE`. There is no compensation: if a call fails midway, already-deleted accounts stay deleted and the person may remain. Deleting a person directly on PersonService leaves orphaned accounts. | `CS/services/CommonServiceImpl.java:174-183`; `AS/services/AccountsServiceImpl.java:54-55`; `AS/entities/Bill.java:35-36`; `AS/entities/Transfer.java:23,29` |
| LEG-14 | **Not-found handling:** unknown account/bill → `404` (`AccountNotFoundException`, `BillNotFoundException`); unknown person → `PersonNotFoundException`. | `AS/exceptions/handler/AccountServiceExceptionHandler.java:14-32`; `AS/services/AccountsServiceImpl.java:34`; `PS/services/PeopleServiceImpl.java:25-28` |
| LEG-15 | **Person validation:** first/last name required, 1–30 chars; birthdate required (`yyyy-MM-dd`); phone required; email required and must be a valid email. | `PS/entities/Person.java:27-45` |
| LEG-16 | **Listing is unpaged:** `GET /v1/people` returns `findAll()`; `GET .../accounts` returns all accounts for the person. | `PS/services/PeopleServiceImpl.java:21-22`; `AS/services/AccountsServiceImpl.java:28-29` |

Existing tests that already exercise rules: `BillControllerIntegrationTest.commitPayment` (LEG-01/02),
`commitPayment_withOverdraft` (LEG-03/04, expects `400`), `commitAdjustment` (LEG-05),
`commitTransfer` (LEG-06) —
`AccountService/src/test/java/ru/kondrashov/accountservice/BillControllerIntegrationTest.java:149-322`.

## 4. Suspected quirks (for human decision — not fixed)

| ID | Suspected quirk | Verdict | Evidence |
|---|---|---|---|
| Q1 | `BillServiceImpl.commitAdjustment` is not `@Transactional`. | **Confirmed.** `commitPayment` has `@Transactional(rollbackFor = Exception.class)` (:75); `commitAdjustment` (:64-71) and `commitTransfer` (:86-95) have no annotation and the class has none either. Each `save` runs in its own repository transaction, so a failure after the bill save leaves the balance changed without a transaction row. For transfers, if the source debit succeeds and the beneficiary credit or `transferService.save` fails, the debit is not rolled back (transfer is **not atomic**). | `AS/services/BillServiceImpl.java:64-95` |
| Q2 | Bill balances are read-modify-written without locking (lost updates under concurrent transfers). | **Confirmed.** `decreaseBillsAmount`/`increaseBillsAmount` read `bill.getAmount()`, compute in memory and `save` (:119-132). `Bill` has no `@Version` and no repository method uses `@Lock`; no isolation level is set anywhere in the repo. Two concurrent debits on the same bill can both pass the LEG-03 check and the second write overwrites the first. (Code inspection; no concurrency test was run.) | `AS/services/BillServiceImpl.java:119-132`; `AS/entities/Bill.java:19-38` |
| Q3 | `hibernate.hbm2ddl.auto = create`. | **Confirmed** in both databases-owning services: the schema is dropped and recreated on every start-up, wiping all data. | `AS-res/hibernate.properties:4`; `PS-res/hibernate.properties:4` |
| Q4 | Plaintext DB password in `application.yml`. | **Confirmed.** `username: postgres`, `password: 12345` committed in both services (test resources use the same). | `AS-res/application.yml:5-6`; `PS-res/application.yml:5-6` |
| Q5 | `FinancialTransaction.time` defaults to server-local `LocalDateTime.now()`. | **Confirmed.** Field initializer uses the JVM default zone, no offset stored. The request DTOs also default `time` to `LocalDateTime.now()` (e.g. `PaymentRequestDTO.java:30`, `TransferRequestDTO.java:30`), so a client-supplied time is accepted as-is. | `AS/entities/FinancialTransaction.java:34` |
| Q6 | `new MathContext(2, HALF_EVEN)` = 2 significant digits, not 2 decimal places. | **Confirmed.** `BigDecimal.round(MathContext)` uses precision = significant digits. Checked with `jshell`: `1234.56 → 1200`, `0.0123456 → 0.012`. Because LEG-07 also converts same-currency amounts, every payment/adjustment/transfer amount is affected: replaying the exact `exchange` code against Moneta 1.4.2 on JDK 8 gave `EUR→EUR 1234.56 = 1.2E+3` (a 1234.56 EUR payment on an EUR bill debits 1200). | `AS/services/JavaMonetaApiCurrencyExchange.java:34` |
| Q7 | Moneta fetches exchange rates over the network via default providers. | **Confirmed (by configuration and a standalone replay; not traced inside the running service).** `getConversion(targetCurrencyUnit)` passes no provider, so Moneta's default chain is used. On Moneta 1.4.2 that chain is `[IDENT, IMF, IMF-HIST, ECB-HIST, ECB-HIST90, ECB]` (printed by `MonetaryConversions.getDefaultConversionProviderChain()`). The bundled `javamoney.properties` configures the ECB and IMF providers with `startRemote=true`, remote URLs (`https://www.ecb.europa.eu/stats/eurofxref/eurofxref-daily.xml`, `https://www.imf.org/external/np/fin/data/rms_five.aspx?tsvflag=Y`) and scheduled reloads (ECB every 3 h, IMF every 6 h), falling back to rate files bundled in the jar. Results therefore depend on network reachability and on when the rates were loaded. There is no rate pinning, no audit of the rate used, and conversion runs inside the request path. | `AS/services/JavaMonetaApiCurrencyExchange.java:32` |

### Other observations (not in the ticket's list, recorded for completeness)

- `Account.creationDate` is annotated `@CreatedDate` with `AuditingEntityListener` (`AS/entities/Account.java:21,33`), but no `@EnableJpaAuditing` exists in the repo, so it is only set if the client sends it.
- The CommonService "new transfer" page (`CS/controllers/CommonController.java:101-107`) adds `people` to the model but the template iterates `${currencies}`, and its form posts to `/common/v1/create/accounts/{accountId}/bills/{billId}/transfers`, for which no controller mapping exists (`CS-res/templates/bills/transfers/new.html`). The transfer UI is not functional.
- CommonService single-item pages call `.findFirst().get()` without a presence check on edit/update routes (`CS/controllers/CommonController.java:149,170,179,220`).
